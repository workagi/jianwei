# AIHOT × 见微：优化后综合评估

日期：2026-10-02。评估对象是见微本地当前工作区，包含此前尚未提交的变化阅读优化，不是 GitHub 上已发布的 v0.2.0。AIHOT 主分支通过 `git ls-remote` 核对为 `3343fe2b20db4be7269113752d82d3992fc52b6b`，与本地比较快照一致。

结论：见微已有可用的多源采集与中文阅读基础；稳定事件身份、原文修订和阅读版本是有价值的进步。但“关注变化”还没有完成持续处理、长期身份和完整阅读三项契约，暂宜作为待修正的预览能力。下一轮优先修通这些链路，再验证真正的精选质量；不应先扩成复杂事件平台。

> 后续实施：本文及9组探针结果是修改前基线。修订自动分析、进度式投影、旧事件更新、完整历史、统一证据、组合监控与导航修正在 [变化阅读优化](change-reading.md) 中记录；真实提取/精选效果评测和采集分析解耦仍待验证，不将本文旧缺陷结果改写为新实现的现状。

## 产品边界：要明确见微为谁完成哪件事

AIHOT 的主要闭环是“固定行业标准→编辑精选→事件/热点→网站与刊物/Agent出口”。见微的适合方向是“一个工作台拥有者→自己的关注范围→值得阅读的更新→减少重复寻找”。这是对产品机制的判断，不是已经测得的商业效果。

当前见微前台可读、写操作要求管理员登录，事件阅读状态只按 `event_id` 全局保存。它能服务同一个拥有者的多设备工作台，但不是每个访客都有个人状态的公开信息产品。保留这个边界可以省去账户体系、组织权限与个性化数据层；需要在首页、首次配置和部署说明中明确。

建议把近期承诺限定为：在已接入来源中，让拥有者持续看到与关注范围有关的新增或修订材料，保留原文核对入口。不要承诺全网完整召回、独立事实核验、全自动判断业务影响或替用户行动。

| 维度 | AIHOT 已提供的机制 | 见微当前状况 | 建议 |
| --- | --- | --- | --- |
| 用户目标 | 行业编辑与公开发布 | 可配置个人采集范围，但任务仍依附平台监控 | 先做好一个拥有者的信息工作台 |
| 内容决策 | 可配置行业标准、标注评测与阈值扫描 | 文档分与任务分分开，但真实推荐校准不足 | 学习评测与错例迭代，先不复制双评分 |
| 事件消费 | 事件详情、综述、报道时间线与人工纠错 | 稳定ID及版本已具备，详情和未读覆盖不完整 | 补历史与纠错入口，复用已有记录 |
| 执行架构 | 原稿落库后按文章入处理任务 | 采集批次中等待分析，修订自动接管缺口 | 先接通待处理状态，再评估单一分析队列 |
| 内容出口 | 一个公开读取层服务网站、刊物、RSS/API/MCP | 网页有阅读层，但证据加载在视图间不一致 | 先统一网页阅读结果，之后再增加一个有用出口 |

AIHOT的架构与公开范围见 [架构说明](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/docs/architecture.md)；编辑评测见 [精选与校准](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/docs/selection.md)。没有同样本实测证据证明它的真实精选质量必然更高。

## 优先修正的已复现问题

### 1. 原文修订没有自动进入新分析（P1）

调用链：`repositories.ts:281` 清空旧摘要、字段和文档评分并设 `pending` → `ingest-items.ts:295` 对已知来源身份或URL跳过新分析 → `worker/index.ts:1158` 只补跑 `failures` → `summary-backfill.ts:267` 只选 `analysis_status='failed'`。

数据库结果：收到完整更正后 `contentRevision=2`、`analysisStatus=pending`、`aiSummary=null`；调用与Worker相同的自动补跑范围，候选为0；任务精选卡片为0。可以通过后台手动补跑恢复，但自动路径不会接手。

这是上一轮实现尚未接通的链路，不只是将来增加队列的理由。先复用现有版本、分析领取和补跑方法，明确“收到的新修订待分析”与“为旧成功内容重新润色”的差别，自动处理前者；不要把所有历史空摘要无条件重跑。

验收：收到修订后，无需再次采集或人工补跑，能重新分析当前输入；旧结果仍不能覆盖新版本，已有回执与用量规则继续生效。

### 2. 有界投影没有处理进度，窗口外材料会持续饿死（P1）

`event-projection.ts:50–52` 每次取最近14天、按发文时间倒序的最多2000条，随后才跳过已处理成员。这个查询限制的是候选扫描，不是本轮尚未完成的工作。

数据库结果：2000条较新的、已处理的材料占位；一条两天前尚未处理的材料，连续刷新两次仍没有事件归属。重复运行同一个窗口不会产生处理进度。变化视图要求已有事件归属，因此这类材料不会出现在变化页；其它视图可能仍显示单篇。

建议分开“本轮待处理材料”和“用于判定关系的有界上下文”。待处理按修订/字段处理进度选择，关系候选仍保留明确上限。无需把2000改成无限，也不需要先引入向量库。

验收：已有材料不能长期阻挡新待处理项；停止新增后积压可以在有限轮次内处理完。将本轮处理数和积压暴露到现有内容状态中，而非只显示Worker存活。

### 3. 近期窗口被误用为长期关注生命周期（P1）

投影只加载近期文章作为事件根节点；`canJoinEventStory` 同时限制根节点与新材料相距14天。关注状态绑定旧事件ID，窗口消失后不会自动跟随同一对象的新事件。

数据库结果：关注20天前开放的 Agent 2.0；今天暂停访问。新材料得到另一个事件ID。普通变化视图有1个事件，“只看已关注”有0个。

另一组结果：20天前的原文今天被更正，正文已到第2版，事件成员仍处理到第1版、事件版本仍为1。对已有文章的修订，本来不需要重新判断事件归属，却同样被原发文时间过滤。

建议明确两层：近期事件分组继续保守；已归属材料的修订按修订进度接手，不按原发文时间排除。长期关注需要明确对象与版本的持续身份，或者将目前按钮清楚限定为“跟踪这次近期事件”。不要用不受限的标题相似关联代替长期对象身份。AIHOT的行业事件阅读不能直接替见微解决个人长期关注。

验收：一个月前的已归属文章今天更正能触发该事件变化；对于明确受支持的长期关注对象，一个月后的新动作不会静默丢失。

### 4. 未展示的变化可以被一起标成已读（P1）

`event-reader.ts:29` 只加载事件当前版本之前最近三个版本，不读取用户的 `readRevision` 来计算尚未读过的范围；卡片按钮却提交整个 `eventRevision`。

数据库结果：已读到第1版，事件当前第6版；页面只返回6、5、4版。点击标记已读后，未读条目变为0，第2、3版没有前台读取入口。当前卡片也没有综述能保证它们已被涵盖。

建议保留有界读取，增加“另有N个未展开变化”和加载更早未读的入口；或者把跳过行为明确命名为“全部标记已读”，并保留完整历史可查。别把显示三个版本当成看完所有变化。已有进展表足以提供历史，不需要再造事实表。

验收：读者能看到尚未读过的范围，或明确选择跳过；证据加载仍有分页上限。关注后没有新变化的事件也应有管理/回看入口。

## 产品能力与内容可信度

### 5. 原文引用存在，不等于结构化字段受原文支持（P2，扩展自动判断前处理）

`parseEventSignal` 校验字段格式和引用是否为原文子串；不校验阶段、数值或范围是否与引用一致。

纯函数结果：原文是“Acme Agent 2.0 is not available yet. The monthly price is USD30.”；传入 `stage=available`、`value=USD0/month`，引用使用原文中的完整句子，仍被接受。该样例验证校验边界，不代表真实模型一定会输出这种错误或已测得其发生率。

建议先做真实提取评测，单列实体、版本、阶段、数字与日期的错误。对可确定的矛盾，在唯一模型输出入口复用现有阶段规则、数值核对并丢弃有问题的字段；无法确定则保留证据和待核对呈现。无需让第二个模型检查每条，也不宜用无限正则制造“已事实核验”的假象。引用校验、语义一致性与事实真实性应分别描述。

AIHOT 的写作规则和实体检查可以提供局部参考，不能当完整事实核验器。单次分析提取字段的当前设计应保留，是否增加调用要由错例和收益决定。

### 6. “关注任务”仍是采集监控，相关性评分不等于个人必要性（P2，产品方向）

`monitors` 每行必须有一个 `platform` 和 `connectorId`；查询按该行的 `item_matches` 过滤。综合首页可以选择各平台的监控，但选中一个并不意味着形成跨X、公众号、搜索的同一关注对象。最近改动统一了门槛和排序，并没有改变这个数据语义。

`deriveMonitorRetention` 仍是文档分加关键词、类型和标签奖励。纯函数结果：配置 MCP 和教程软偏好，输入无关融资公告，文档分85，仍保留且任务分85。这是当前软偏好的政策，不能直接判作所有情况都应丢弃，但也不能宣传为已经判断出“对我的MCP任务很重要”。目前摘要分析也没有读取用户任务目标或已读事实。

建议先让一个关注视图组合若干现有监控，以显式必含词、变化类别表达范围；清楚区分硬条件与排序偏好。任务分应显示来源和解释。第一版无需自然语言目标推理、知识图谱或行动Agent。

### 7. 精选与变化视图读取了不同的证据能力（P2）

只有 `loadReaderFeed` 的 changes 分支加载 `loadEventDevelopments`；featured、latest、archive和收藏使用相同 `TimelineCard` 和读状态按钮，但没有加载进展证据。

数据库结果：同一第6版事件，精选卡片有版本6，进展证据行数0。旧代表稿提示“请结合最新变化的原文证据”，但该视图可能没有这份证据。用户可以在那里标记整个当前版本已读。

建议在最终可见事件列表上共享证据加载，或链接到统一事件详情；避免四个视图分别补一套逻辑。AIHOT值得借鉴的是一个读取契约，而非必须拆出独立API服务。以当前单体规模，Next.js+Worker+PostgreSQL足够。

### 8. 新发现旧稿与事情新发生的时间表达不充分（P2）

数据库结果：十天前发布的材料今天首次入库，出现在最近一天的变化候选中，卡片日期是今天，标签为“首次收录”。当前行为可以合理表达“我新看见这篇文章”，但界面“关注任务的新变化”及按日分组会让人把它与“事情今天变化”混淆。模型给出发布阶段时，这种差别更难辨认。

建议保留原发文时间和首次发现时间，两种情形明确标注；冷启动/新信源导入先建立阅读基线，可按用户选择展示存量。AIHOT 将旧稿和回灌按原文时间归档的原则值得借鉴，48小时数字不必照搬。

## 技术架构：真正需要调整的依赖

当前优点应保留：页面不调用模型；外部调用在数据库事务之外；文档、来源观察与监控命中已分层；付费回执和预算已有共享机制；原文修订与慢结果写入有版本校验。这些地方没有发现必须继续增加保护层的理由。

仍有两项结构约束（代码路径确认，未做故障或负载实测）：

1. **原始采集结果先等待分析再提交。** `runMonitor` 在 `prepareIngest` 中完成模型调用之后，才事务提交原文与匹配。模型延迟直接延后原稿可见性；期间中断需重新采集才能恢复输入，回执只保存调用结果，不代替原始采集持久化。不要夸大为每次一定丢数据，游标与上游回看仍可能帮助恢复。
2. **事件更新依赖整轮批次结束。** `runOnce` 等所有本轮监控完成，再做失败补跑及事件投影。快来源即使已提交原稿，也要等慢监控和补跑完成才进入变化视图。Worker心跳正常不能说明这条阅读链路已及时完成。

AIHOT 的可借鉴原则是原稿先落库，按具体文章/修订推进处理；见微可先复用现有pending状态和分析领取来接通有限批处理。如果实际并发与恢复需求证明需要队列，现有依赖已包含pg-boss，优先一个分析任务入口即可，不复制其完整队列矩阵、三服务部署或更多保活任务。

读取方面，精选每个平台最多5000条完整记录再在内存分组，变化最多5000条材料而不是5000个事件；同一热门事件的重复材料可能挤占别的候选。当前SQL也重复选择来源、匹配与代表材料。优先设计待处理查询与事件级分页，实际量级下用EXPLAIN和延迟测量再决定索引或缓存；本轮没有测得性能瓶颈，不建议为假设负载加入Redis、搜索集群或向量库。

## 用户体验与运营闭环

以下由源码确认，尚未重新做浏览器可用性测试：

- 未登录时仍显示关注/已读按钮，点击后才提示去管理后台，缺少直接登录及返回当前筛选的流程。明确一个工作台拥有者后，改善入口即可，不必建设普通用户注册系统。
- 只有“未读且已关注”的过滤，没有所有已关注事件目录或稳定事件详情路由；已读无新变化后不容易回看和取消关注。文章收藏无法替代事件管理。
- 事件误合并只能通过CLI拆分；没有低成本标记“不相关/合并错了/摘要有误”的入口，也没有完整的人工合并修复流程。先支持已有拆分操作与收集少量错误样本，不需要完整编辑CMS。
- 点击主题标签会丢失搜索和“只看已关注”，清除主题也未保留followed；用户当前范围可能被悄悄扩大。各视图的查询参数应复用同一个小构造方法。
- 首页“最近更新于”使用当前渲染时间，不是最新采集/事件时间。空变化页不能区分已读完、没有配置、分析积压和投影未完成；侧栏心跳只说明服务状态。复用现有采集运行与pending统计解释当前结果，不再加一套监控服务。

首次使用应围绕一个最小成功路径：接入一种来源→明确关注范围→收到第一条真实材料→看到有证据的变化→读完后同样材料不再打扰。原生RSS以后有助于降低只读RSS用户的部署成本，但先修这条路径，比扩大Provider清单更有价值。

## 评测与成本：当前缺少产品效果证据

当前事件评测主要检查给定正确字段后的成对关系；16个构造难例与3对人工标注实际材料不能验证模型提取、最终事件组、长期关注、候选覆盖或推荐效果。本轮又复现了已有集成测试之外的状态路径，说明“380测试通过”不等于整个阅读契约已验证。

AIHOT的标注样本、开发集/留出集、阈值扫描和错例工作台更值得借鉴。见微可先补固定真实材料与机器可读报告，不必先建设评测后台。避免为了过某个测试而制造更多保护分支。

建议用同一批事件及其重复报道、后续材料建立序列评测，先覆盖50–100对真实难例及若干完整任务序列。重点衡量：

| 指标 | 为什么比功能数量更有用 |
| --- | --- |
| 必须看到的变化在前K条是否出现 | 直接检验任务召回、候选截取和排序 |
| 已读后重复报道造成多少次提醒 | 衡量减少打扰的实际效果 |
| 修订到可阅读变化的时间与遗漏 | 检验采集、分析、投影是否真正接通 |
| 实体、阶段、数字/范围提取错误 | 防止带原文引用的错误结构化字段影响事件 |
| 每条有效变化的调用数、费用和等待 | 区分处理很多材料与交付有效结果 |
| 读懂一条变化所需时间及回看成功率 | 衡量证据、历史和导航是否改善阅读 |

保留现有请求/用量统计，先在离线评测输出中联结这些指标。没有真实样本证据前，不提高模型调用层数，也不声称节省了某个百分比的时间或费用。

## 建议的实施顺序与必要性

| 顺序 | 最小范围 | 复用方式与交付条件 |
| --- | --- | --- |
| 1 | 接通修订pending；待处理投影能推进；旧稿修订不被发文窗口排除 | 复用现有状态、领取和事务；新增原文能走到当前版本分析与事件 |
| 2 | 所有读操作有证据/历史入口；未展开变化明确；长期关注边界清楚 | 复用进展表与查询；用户不会无意消耗未展示变化 |
| 3 | 真实事件序列和精选留出评测；修正明确的字段矛盾 | 复用一次分析和现有离线评测；先证明质量再调模型/阈值 |
| 4 | 一个关注视图组合现有监控；硬条件与软偏好可理解 | 用户能表达自己要看的变化，避免重新造采集体系 |
| 5 | 根据观察到的延迟/恢复问题拆分采集与分析；再考虑一种输出 | 单一分析入口或有界pending扫描优先；日报/通知须复用验证过的阅读结果 |

暂不建议：通用知识图谱、多Agent编辑流水线、所有材料双评分/多供应商核验、复杂价格状态机、多租户账户、全套热门榜和日报周报月报同步上、为每种失败再增加一层恢复框架。AIHOT的完整行业站是另一种规模的交付，不是见微当前的功能清单。

对已出现但没有作用的代码，应优先删除。例如 `content-retention.ts:186` 留有排除关键词硬Gate之后的零值罚分“安全网”，它不能改变任何当前判断。这样的预留分支比新增保护更值得清理，但优先级低于上述阅读与处理缺口。
