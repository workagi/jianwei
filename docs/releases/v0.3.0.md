# 见微 v0.3.0：变化阅读与低资源部署

这版让阅读围绕事件的实际变化展开：关注、已读和进展版本保存在数据库，重复报道或更换代表稿不会重新提醒；原文更正能够重新分析并保留证据。采集先保存原稿，模型在后台小批推进，核心部署默认只常驻 PostgreSQL、Web 和 Worker。

## 阅读与内容

- 默认进入关注变化，支持事件关注、按版本全部标记已读、已关注目录及稳定详情页；文章收藏继续独立保存。
- 事件身份、代表稿与进展时间分开；记录预告、开放、限制和更正，分页核对原文证据与修订 HTML。
- 原文修订自动重新分析，旧采集、全文补抓和旧分析结果不能覆盖更新输入。
- 组合已有监控作为阅读范围，筛选、相关分、理由和导航保持一致；任务精选与公共精选采用各自准入标准。
- TOP 在浏览卡片截断前选择，不再把转载数量当作独立核实或直接排名加分。
- 在原有一次分析中提取带引用的事件字段，辅助跨语言归并和进展识别；不增加第二层模型调用。

## 执行与资源

- 原稿先落库，单个 Worker 同时推进一批后台分析，默认每批最多 5 条；慢分析不阻塞下一轮采集。模型关闭时保留可恢复待办。
- 自动待处理与未自动排队的历史材料分开统计，跨平台按原稿去重；数据库读取失败明确展示不可用状态。
- 变化/关注列表分页读取候选与成员，仅为当前页加载完整卡片字段；普通已分析长文按需返回短预览。
- 默认采集并发 2、模型并发 2、每应用进程连接池 4。终态运行明细分批清理，普通记录默认 30 天、异常 90 天；原文证据、响应回执与预算账本保留。
- Worker 独立打包为精简运行镜像，Web 和迁移工具独立构建。Release 发布四个组件的 amd64/arm64 版本镜像，支持拉取部署以避免服务器编译。
- 修复升级测试的旧迁移数量断言及回执维护命令启动错误，并将维护命令加入 Docker CI。

构造长文样例中，两并发精选的 Web RSS 峰值约 499→220 MiB；这不是整机容量认证。不同阶段的资源、延迟与取舍见 [低资源记录](../low-resource-optimization.md) 和 [最新读取记录](../reader-and-queue-optimization-2026-10-03.md)。

## 从 v0.2.0 升级

先保留旧代码和环境配置，备份数据库与 `APP_ENCRYPTION_KEY`；不要更换加密密钥。以下命令使用生产项目名 `jianwei`，自定义项目应使用原来的项目名、配置文件和路径。

1. 停止旧 Web/Worker，再备份仍运行的数据库：

   ```bash
   docker compose --env-file .env.production -p jianwei -f docker-compose.prod.yml stop web worker
   JIANWEI_COMPOSE_PROJECT=jianwei ./scripts/backup-db.sh ./backups
   ```

2. 拉取代码并切换版本：

   ```bash
   git fetch origin --tags
   git switch --detach v0.3.0
   ```

3. 确认需要的采集服务。在 `.env.production` 设置 `COMPOSE_PROFILES=wechat`、`trendradar` 或 `wechat,trendradar`；留空只启动核心服务。**旧监控不会自动停用**，关闭采集器前应先停用对应监控，或配置可访问的外部服务。

4. 源码构建与启动：

   ```bash
   docker compose --env-file .env.production -p jianwei -f docker-compose.prod.yml up -d --build --wait
   ```

   或者在确认镜像可访问后，设置 `JIANWEI_IMAGE_TAG=v0.3.0` 并使用版本镜像：

   ```bash
   docker compose --env-file .env.production -p jianwei \
     -f docker-compose.prod.yml -f docker-compose.images.yml \
     up -d --no-build --pull always --wait
   ```

5. 迁移服务执行 0029–0033，增加事件进展、阅读状态和原文修订等字段/表。核对 `/api/health`、后台登录、Worker 心跳、关注/已读状态与分析待办。首次投影建立阅读版本需要后台推进；历史未标记 pending 不会自动全库分析。

本机部署使用 `.env` 和 `docker-compose.yml`，可设置 `JIANWEI_IMAGE_TAG=v0.3.0` 后运行 `./start.sh`。发布源码或镜像不会自动升级正在运行的实例。

## 镜像与维护

版本镜像为 `ghcr.io/workagi/jianwei-{web,worker,migrate,werss}:v0.3.0`。新镜像由标签工作流构建，四个组件完成后才创建 Release；首次发布需核对包可见性与拉取权限。可选 TrendRadar 继续使用原固定上游版本。

维护命令改在一次性工具容器运行，精简 Worker 不再包含 pnpm 和源码脚本：

```bash
docker compose --env-file .env.production -p jianwei -f docker-compose.prod.yml run --rm --no-deps migrate pnpm model:receipts list
docker compose --env-file .env.production -p jianwei -f docker-compose.prod.yml run --rm --no-deps migrate pnpm events refresh
docker compose --env-file .env.production -p jianwei -f docker-compose.prod.yml run --rm --no-deps migrate pnpm events split <item-id>
```

使用版本镜像部署时加上 `-f docker-compose.images.yml`。核对服务商记录后，可用同一方式执行 `pnpm model:receipts retry <receipt-key>`，只放行超过 30 分钟且结果不明的请求；下一次请求可能产生新费用。

## 验证与边界

本地隔离验证包括 409 项功能/数据库回归、生产构建、类型与审计检查、带数据的 v0.2.0 升级、最新 arm64 镜像及浏览器阅读流程；升级脚本与回执命令修复另有真实工具容器验收。正式发布还要求对应合并提交的完整 CI 成功。

- 单用户自托管定位保持；规则黄金集仍有质量缺口，原文引用不等于独立事实核验。真实精选、任务召回和模型提取尚未完成留出评测。
- 核心 1 核 / 2 GB 是小规模优化目标，未验证真实采集峰值或长期 Linux 整机容量；开启公众号与热榜需要额外资源。
- 小批后台分析可能积压，吞吐取决于模型延迟、配额和输入量。默认模型输出上限提高至 1,000 tokens，未测得真实费用节省。
- 原生 RSS Provider、前台人工拆分与推荐校准尚未实现。数据库仍会因原稿、修订和证据增长。

## 回滚

停止新版应用，使用升级前数据库备份、同一加密密钥和对应旧代码恢复。仅降级应用镜像不能恢复新版本期间写入的状态；不要删除新表或倒跑迁移。恢复备份会失去备份之后的数据，按 [生产备份与恢复流程](../production-deploy.md)操作。
