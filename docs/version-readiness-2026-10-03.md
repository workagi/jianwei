# 见微优化收益与版本发布评估

评估日期：2026-10-03。已发布基线为 [v0.2.0](https://github.com/workagi/jianwei/releases/tag/v0.2.0)，提交 `4c567273ce734ba053958867cb5a55ea885d6e98`。评估对象是该提交之后的本地未提交工作区；本轮没有修改业务代码、提交、推送、打标签或部署。以下验证只使用一次性 PostgreSQL、本地生产构建与候选镜像，没有生产数据、真实采集或付费模型请求。

## 发布结论

建议下一个版本为 **v0.3.0：变化阅读与低资源部署**。功能、数据库和部署方式的变化已经超出补丁版本范围，但还不足以证明 1.0 的产品效果与容量。

**初次评估时不宜直接推送正式版本标签。** 当时复现了两个具体缺陷：数据库升级 CI 脚本仍要求旧迁移数量；模型回执维护命令不能启动。应先用小改动修复这两处，补齐版本号和正式发布说明，通过当前提交的完整 CI 后发布。无需在本次版本前继续扩大业务功能。

**同日后续：两处缺陷已修复并通过针对性验证。** 升级脚本从当前 journal 计算记录数，增加新版本表/字段与旧稿修订号断言；回执命令复用异步 main 入口。隔离库 0023→0033 升级通过，真实 tools 镜像的列表、过期放行、活跃/成功请求拒绝及错误退出码通过。既有 6 项回执测试、类型检查、ESLint 和 ShellCheck 通过。CI 增加维护命令冒烟；完整远端 CI 尚未运行。结果见 [小修验收](reviews/2026-10-03/release-small-fixes-results.json)。仍需版本号、正式说明及提交后的 CI，不代表已经发布。

远端 main 仍是 v0.2.0 的提交；其 CI 和 Release 成功不能证明当前工作区通过远端验收。`package.json` 仍为 `0.2.0`，本轮也没有创建正式的 `docs/releases/v0.3.0.md`。

## 产品能力的实际变化

| 维度 | v0.2.0 的基础 | 当前新增能力与边界 |
| --- | --- | --- |
| 阅读对象 | 已有持久事件与文档精选 | 默认关注变化，事件身份、代表稿、进展时间分开；按事件版本持久保存关注与已读。重复转载和换代表稿不重新打扰，明确的新阶段或修订形成变化。状态属于单用户工作区。 |
| 修订与证据 | 原稿与分析已有防重复机制 | 保存原文修订及 HTML，修订重新分析，过期分析与全文补抓不能覆盖新输入；详情页分页查看进展证据。原文引用可以核对，不代表事实经过独立核实。 |
| 个人任务 | 已有监控匹配分 | 可组合已有监控，跨平台筛选、相关分与说明使用同一范围；任务精选和公共文档质量门槛分开。相关分仍不是经过用户反馈校准的个人必要性。 |
| 选择与排序 | 有界精选、事件归并 | TOP 在浏览卡片截断前选择，移除报道数量的加分；大事件按批读取，不再让大量重复稿挤掉其他事件。仍有候选边界和规则误判。 |
| 后台执行 | 已有租约、预算和响应回执 | 原稿先提交，分析在同一 Worker 小批后台推进；慢模型不阻塞下一轮采集，模型关闭时保留可恢复待办。没有新增独立队列服务。 |
| 可理解性 | 展示采集与分析状态 | 自动候选与未自动排队的历史材料分开，跨平台按原稿去重；真实数据库读取失败展示不可用状态。模型/额度/租约仍可能使候选暂时不被处理。 |

与此前 AIHOT 固定快照的比较，原稿修订、编辑对象分层、变化语义和采集分析分离已经落实。见微保留自己的可配置监控定位，并增加事件版本阅读基线。AIHOT 更值得继续借鉴的部分是实际标注、留出评测与错例迭代；目前不能证明见微的精选质量达到或超过它。比较依据见 [产品机制审查](aihot-product-review-2026-10-02.md) 和 [后续综合评估](aihot-current-assessment-2026-10-02.md)，不是对 AIHOT 最新代码的重新评测。

不能给出一个可靠的“整体提升百分比”。下面分别列出有证据的资源与读取收益，不能将不同阶段、负载和测量口径合并成总分。

| 指标 | 前 / 后 | 变化 | 证据范围 |
| --- | --- | --- | --- |
| 默认常驻核心服务 | 7 / 3 | 减少 4 个 | 本轮实际解析 v0.2.0 与当前 Compose；迁移是一次性服务。生产另有 Caddy，公众号和热榜按需启用后仍占用资源。 |
| 两并发精选 Web RSS 峰值 | 499.47 / 219.98 MiB | 下降 56.0% | 资源优化阶段，2,000 篇构造长文、300 个事件；不是最终代码的整机压力复测。 |
| 变化页 HTTP 耗时 | 2,317 / 472 ms | 下降 79.6% | 同一资源优化阶段；单轮请求，长文具备可复用的分类与摘要字段。 |
| Web 构建进程树 RSS 峰值 | 1,166 / 835.75 MiB | 下降 28.3% | macOS 有缓存构建，共享页可能重复计数；耗时由 16.88 增至 19.63 秒。 |
| 两万条同源重复材料读取 | 7,621 / 5,177 ms | 缩短 32.1% | 最新阶段的旧流程复现与最终流程；SELECT 202→104，完整展示查询 100→1。每阶段一轮，旧流程省略最终证据查询。 |

前四项中的 HTTP/构建记录见 [低资源优化](low-resource-optimization.md) 与 [原始资源评估](resource-and-product-assessment-2026-10-02.md)；最后一项见 [阅读与待办优化](reader-and-queue-optimization-2026-10-03.md)。资源优化前基线已包含一部分产品优化，不能当作所有指标均与公开 v0.2.0 直接对照。

最新两万条读取的验证进程 RSS 为 173.84→183.34 MiB，没有进一步降低；空闲 Web 也没有明显变小。5.2 秒仍有交互性能问题。默认 1 核 / 2 GB 是核心小规模部署目标，未获得 Linux 整机、真实采集峰值和长期运行的认证。

按本轮开始时的差异统计，业务运行代码涉及 40 个文件，增加 1,337 行、删除 477 行，净增约 860 行；测试净增约 1,155 行。迁移元数据另外约 14,245 行，不能把生成快照与业务复杂度混为一谈。这不是代码越少越好的证明，但本轮主要复用了 PostgreSQL、已有状态、回执和 Worker，没有引入额外常驻缓存或队列组件。

模型分析仍复用一个入口，但默认输出上限由 OpenAI 兼容路径的 420、Claude 路径的 300 提高至 1,000 tokens。没有真实费用测量，不能宣称模型成本下降。

## 初次发现的两处缺陷（已修复，保留复现证据）

1. **升级 CI 的旧断言。** `scripts/test-upgrade.sh:122–123` 固定要求迁移记录数为 6，并输出“通过 0028”。从脚本的 0023 夹具升级到 0033 后实际为 11，所有前置数据检查通过后仍以退出码 1 结束。最小修复是根据当前 journal 中 baseline 之后的迁移数量验收，并更新输出；同时增加对新版本关键表/字段的升级断言，避免只验旧结构。本轮为了使用本机 PostgreSQL 容器及已安装工具，使用临时 psql 适配器并把临时副本中的 `pnpm db:migrate` 换成相同的 drizzle-kit 二进制；保留原始迁移和全部断言。
2. **回执维护命令无法启动。** 最新 tools 镜像执行 `pnpm model:receipts list`，报 `Top-level await is currently not supported with the "cjs" output format`，退出码 1。文件与 v0.2.0 一致，属于本轮发现的遗留问题，不是精简镜像引入的回归。采用已经在 `scripts/events.ts` 使用的异步 main 入口即可，无需改变模型处理机制。精简 Worker 已不包含 pnpm/脚本，新的维护说明应使用一次性 tools/migrate 容器。

## 可以随版本公开的边界

- 内容规则黄金集 96 个案例、180 个断言，通过率仍为 65.0%，macro F1 63.4%；没有达到现有 80% / 75% 质量目标。它是分类、标签和准入的组合规则评测，不是精选效果或模型提取准确率。
- 16 对构造标题规则样例仍有 1 对误合并、2 对漏合并；不能用该结果推导模型辅助归并的生产准确率。实际精选、任务召回和模型字段提取需要独立真实留出集。
- 单批默认 5 条、默认 60 秒轮询，理想自动处理节奏约 300 条/小时；真实模型耗时、配额与失败会降低吞吐。高输入量仍可能积压，不能称为高吞吐系统。
- 前台人工纠错与原生 RSS Provider 还没有实现；RSS 部署仍依赖已有 TrendRadar 路径。
- 保留了原稿与证据，也意味着总体数据库增长仍存在；运行明细清理只解决一部分增长。

这些影响宣传范围与下一阶段优先级，不必全部完成后才能发布 v0.3.0。下阶段应先用真实错例和目标机器确定质量、吞吐与容量，再决定是否需要增加代码。

## 建议发布说明草案

**见微 v0.3.0：关注变化，降低核心部署负担。**

- 新增事件关注、按版本已读与进展证据回看；重复报道和代表稿替换保持阅读状态。
- 原文修订自动重新分析，组合监控可形成阅读范围，任务精选使用对应相关性。
- 原稿先保存，分析小批后台推进；自动待办与历史未排队材料分开显示。
- 默认核心三服务，公众号与热榜按需启用；独立 Web、精简 Worker 与迁移工具镜像，提供版本镜像部署入口。
- 长文样例的阅读内存与构建峰值降低；具体测试条件、性能取舍和容量限制见优化记录。

升级前备份数据库，停止旧 Worker，使用同一版本的应用和迁移工具执行 0029–0033，再验证登录、事件变化、关注/已读、队列与心跳。历史未标记 pending 不会自动全库分析；停用可选采集服务前需停用对应旧监控。维护命令转入一次性 tools/migrate 容器。数据库回滚应结合升级前备份，不把降级应用镜像视为完整回滚。

正式发布时按 [版本发布流程](release-process.md)：修复两处缺陷 → 更新版本和发布说明 → PR 全部 CI → 合并提交 push CI → 标签 → 四个组件双架构镜像 → GitHub Release → 验证镜像可见性与可拉取性。若要对外承诺最低机器配置或高质量精选，应先补对应验证，不在本次说明中承诺。
