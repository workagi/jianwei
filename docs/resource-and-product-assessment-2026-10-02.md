# 见微：后续优化与机器要求评估

日期：2026-10-02。对象为当前本地工作区，包含之前的变化阅读改动；不是已发布版本。本轮只做源码审查和隔离资源测量，没有修改业务代码或部署配置。

结论：还有值得处理的问题。下一轮优先减小阅读查询、贯通轻量部署、移走服务器构建；这些能直接减少本机承担的工作。保留 Next.js + Worker + PostgreSQL，不需要为降低配置重写框架或增加缓存服务。真实精选质量与采集/分析处理顺序仍需完善。

## 一、机器开销的实测依据

本轮新建独立 PostgreSQL 17，构造 2,000 篇长公众号文章、300 个已归属事件，正文与 HTML 共 160.23 MiB。数据库限制为 1 CPU / 512 MiB；Web 在 macOS 上运行当前 standalone 生产构建，Node 堆上限 512 MiB。没有连接生产库、调用模型或采集上游。

| 场景 | Web RSS | HTTP 耗时 | 响应 |
| --- | ---: | ---: | --- |
| 服务就绪，尚未访问阅读页 | 106.64 MiB | — | — |
| 精选页，单请求 | 峰值 323.48 MiB | 2,240 ms | 200；约 210 KB HTML |
| 变化页，单请求 | 峰值 338.12 MiB | 2,317 ms | 200；约 278 KB HTML |
| 精选页，两个并发请求 | 峰值 499.47 MiB | 各约 4,510 ms | 均为 200 |

这是短时构造负载，不是整套服务用量，也不是长期容量结论。各请求场景在同一个 Web 进程中顺序执行，后续峰值可能包含前一次分配；不能简单相减当作单请求的独立内存成本。未测浏览器采集、Linux cgroup、真实模型等待或长期 GC。两并发响应变慢不能单凭本轮结果归因于某个 CPU/数据库瓶颈。

另以独立进程测生产读取函数：精选最终返回 36 条，峰值 RSS 330.56 MiB；变化返回 50 条，峰值 297.81 MiB。只取轻字段的参考查询返回相同数量的候选材料时，峰值 110.23 MiB、耗时 190 ms。参考查询省略了部分生产 SQL、过滤及分组，**不具有相同阅读语义**；它支持缩小读取范围的方向，不能当成已实现的优化效果或节省比例。

当前 Webpack 构建通过，耗时 16.88 秒，主进程及子进程 RSS 合计峰值 1,166 MiB，进程数量峰值 8。macOS 的 RSS 求和可能重复计算共享页，且已有依赖和构建缓存；不能直接换算成 Linux 冷启动 Docker 构建所需内存。

证据：

- [生产服务测量](reviews/2026-10-02/resource-server-results.json)
- [读取函数测量](reviews/2026-10-02/resource-runtime-results.jsonl)与[构造样例/诊断脚本](reviews/2026-10-02/resource-profile.ts)
- [构建测量](reviews/2026-10-02/resource-build-results.json)与[构建输出](reviews/2026-10-02/resource-build-output.log)

脚本的 `--seed` 会写数据库，只可用于独立一次性库，必须设置 `RESOURCE_REVIEW_DISPOSABLE=1`。普通测量模式不改数据，禁用外部 fetch。完成测量后已停止本轮测试 Web 进程和 PostgreSQL 容器。

## 二、优先优化的资源来源

### 1. 阅读页先拉整篇文章，再挑卡片（优先级最高）

`src/lib/reader-data.ts:715` 的变化/关注视图先取最多 5,000 条材料，在内存分组后分页；`730` 的精选每个平台最多取 5,000 条，四个平台最多 20,000 条。`src/db/queries.ts:182、221` 会把每条完整正文与 HTML 一起返回。

这同时造成两种问题：长文放大数据库传输和 Node 分配；同一事件的大量重复材料消耗窗口，让其他事件没有进入候选的机会。单纯把上限从 5,000 降到 500 会牺牲召回，不能解决这个依赖。

最小调整应是：

1. 列表候选查询返回标题、摘要、分类、评分、来源、事件及阅读状态等轻字段；公众号全文就绪用布尔值表达，正文只在详情或确实需要旧数据规则回退时读取。
2. 变化/关注先选事件并分页，再加载页面所需代表材料与证据；精选保留任务范围、平台平衡和排序规则，先缩小候选，再读取最终必要材料。
3. 已有有效分类、标签、分数时，不再提前计算整篇规则回退。`mapRow` 当前会预先执行类型推断、标签推断和保留判定，即使部分结果最终不使用。

不能一律去掉正文：X 卡片展示全文和引用推文，旧数据还依赖正文做分类与主题回退；来源质量检查也有自己的输入要求。应明确读取契约，避免用截断改变原有筛选语义。无摘要长文的摘录也应限定展示长度，CSS 行数限制并不会缩小传给浏览器的字符串。

验收：相同样本下筛选、评分、Top 选择和证据保持一致；大量重复材料不遮住其他事件；测量单请求/并发 RSS、SQL 耗时及响应大小。不要先加 Redis 掩盖每次读取过多的问题。

### 2. 默认启动整套采集服务，轻量部署没有贯通

基础 Compose 默认有 7 个常驻服务：PostgreSQL、Web、Worker、WeRSS、TrendRadar、MCP、刷新服务；生产独立文件再增加 Caddy。迁移是一次性任务，全文增强是可选 profile。

核心功能只有 Web、Worker、PostgreSQL 三个服务。摘要走外部模型 API，没有本地模型权重或 GPU 推理要求。公众号浏览器采集与热榜应由使用者按需启用，也可连接外置服务；外置只是转移部署成本，不能说总成本消失。

已有 `docker-compose.lite.yml` 去掉了采集侧车，但迁移后仍调用通用 seed，创建启用的默认 TrendRadar 监控；Worker 每轮还会进入 WeRSS 授权检查，内部虽然限频，首次仍请求不存在的服务。轻量用户因缺失未选能力而得到错误状态，体验与部署选择不一致。

建议统一核心与可选能力：未启用的本地服务不启动、不自动创建相应监控、不检查其授权。沿用 Compose profiles 就足够；迁移依赖、生产入口和初始化配置一并贯通，避免继续复制独立配置文件。[Docker 官方 profiles 说明](https://docs.docker.com/compose/how-tos/profiles/)

当前 WeRSS 的基础与生产配置也没有传入完全相同的内容自动检查参数，需统一预期；本轮没有测其实际镜像默认行为和采集峰值。已有限频、熔断、串行回填继续复用，不加新的保护框架。

### 3. 服务器现场构建放大安装门槛

`start.sh:222` 默认 `up -d --build`；发布流程只生成 GitHub Release，没有发布预构建镜像。运行较轻并不代表小机器能一边运行服务一边装依赖、编译和迁移。

建议 CI 生成版本固定的 Web/Worker 镜像，服务器拉取运行。本地源码构建保留给开发。Worker 当前使用 `tools` stage，带全部开发依赖与源码，而且 stage 依赖完成 Next 构建；可拆成精简 Worker runner，直接执行已有 `dist/worker/index.js`，迁移工具只用于一次性任务。

本地 `node_modules` 约 896 MB、Web standalone 约 57 MB、Worker bundle 约 1.1 MB，反映打包裁剪空间，**不是内存节省量**；Worker 的必要外部依赖仍需随 runner 提供。

如仍需要在小服务器编译，可另测降低构建并发及 `experimental.webpackMemoryOptimizations`。官方说明该选项降低构建峰值、可能略增编译时间；本轮没有应用它，不承诺收益。不要关闭类型检查换取更低门槛。[Next.js 内存指南](https://nextjs.org/docs/app/guides/memory-usage)

### 4. 并发参数存在，但 Docker 部署调不到

Worker 读取 `WORKER_CONCURRENCY`，默认 4；当前 Compose 没有传入这个变量，写进宿主 `.env` 不会自动改变容器 Worker。摘要并发默认也是 4。`src/db/index.ts:14` 为每个进程设数据库池最大 10；连接按需创建，不是启动就分配 20 个后端。

轻量档可先以监控并发 1–2、摘要并发 1–2、每进程数据库池最大 2–4 为测试起点，明确通过 Compose 传递。降低并发影响处理速度，应测积压消化与修订延迟。`mem_limit` 是上限，不是预留，也不能靠压低上限解决一次查询分配过多的问题。

### 5. 数据增长缺少统一保留策略

原始载荷出现在来源、命中/观察等记录，正文与 HTML 还保存在内容修订中；采集运行、调用记录等运营历史也持续增长。当前未发现覆盖这些历史的统一按龄清理任务。数据库压缩会影响实际磁盘量，本轮没有测长期增长速率。

先量各表及索引的体积/增长，再为可丢弃的运行历史设保留期。事件证据、收藏、关注内容和有幂等作用的调用回执需分别定义生命周期，不能统一“30 天全删”。不要为清理新增一个常驻服务。

## 三、还有哪些产品问题值得处理

此前修订自动分析、投影处理进度、旧稿更新、完整历史、证据统一和组合监控已经调整；旧评估里的缺陷不能继续当成未修复的问题。本轮仍有以下重点：

| 问题 | 实际影响 | 最小下一步 |
| --- | --- | --- |
| 真实精选与提取质量证据不足 | 跑通流程仍可能筛掉重要变化，或展示引用存在但字段判断错误的结果 | 冻结真实材料与完整变化序列，比较前 K 召回、重复提醒、实体/阶段/数字错误与每条有效变化费用 |
| 首次采集先等模型，再提交原稿 | 模型等待延后原稿持久化，并让批次长期保留输入；中断后的恢复依赖再次采集或上游回看 | 原稿与来源先提交为待处理，复用已有修订、分析领取和预算；首版 pending 的处理范围应明确定义 |
| 候选窗口以材料而非事件计数 | 热门事件的重复材料影响覆盖，资源问题也变成产品召回问题 | 事件级候选/分页；不要通过缩小材料上限换低内存 |
| 前台纠错缺少闭环 | 误合并、不相关内容和摘要错误很难成为下一轮改进的样本 | 先复用已有拆分能力，提供少量错误类型与可定位的材料/事件信息，无需完整 CMS |

现有评测覆盖 16 对构造难例和 3 对实际材料的人工字段回归，没有验证真实模型提取、独立精选留出集或完整长期任务。应先补证据，再决定新增规则或模型调用；不要为了“更强壮”不断叠加校验。

产品边界仍宜保持为一个拥有者的信息工作台。组合监控表达关注范围，但不等于模型理解用户的业务目标；结构化原文引用也不等于独立事实核验。近期无需多租户、通用知识图谱或多 Agent 编辑体系。

## 四、AIHOT 借鉴与合理目标

对照 AIHOT 已审查的 `3343fe2b20db4be7269113752d82d3992fc52b6b` 快照：

- 原稿落库后按文章推进处理：可降低模型慢调用与采集提交的耦合，见微先复用已有 pending/领取机制。
- 标注、留出评测与错例迭代：比复制更多评分和判断层更有价值。
- `Dockerfile` 的 `npm prune --omit=dev`：借鉴生产依赖裁剪，见微 Worker 不应长期使用开发工具镜像。
- [日常保留任务](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/packages/backend/src/operations/retention.ts)：区分运行历史、过期文件和可重建缓存；不照搬它的天数，更不把事件证据当缓存删除。

没有在同机器、同样本上测 AIHOT，不能宣称其整体资源更低或推荐更准确。

建议依次交付：①列表轻字段与事件级分页；②真正可用的核心部署、可选采集及并发参数；③预构建镜像与 Worker 生产依赖；④原稿先落库、真实质量评测和运行历史保留。

**核心档 1 核 / 2 GB 是合理的待验收目标，不是本轮已经证明的容量承诺。** README 已列此档，但其空闲用量不能代替运行峰值；配置表应补样本量、请求并发、启用来源、版本及测试环境。目标验证应在 Linux 上包含连续采集、阅读并发、积压消化、迁移和更新；预构建镜像使用场景与源码构建场景分开报告。

包含本地 WeRSS 浏览器、热榜及全文增强的完整档，需要单独测采集峰值，本轮不能把它承诺到同样的 2 GB。没有足够依据承诺 1 GB 稳定运行。优化方向是减少默认启动的组件和每次处理的数据，而不是继续增加运行时保护。
