核对日期：2026-10-02。AIHOT 基线 `3343fe2b20db4be7269113752d82d3992fc52b6b`；见微基线 `4c567273ce734ba053958867cb5a55ea885d6e98`，加上一轮尚未提交的局部修改。

## 2. 综合评定：两边真正处在哪一步

| 能力 | AIHOT 源码体现的机制 | 见微当前机制 | 对见微的意义 |
| --- | --- | --- | --- |
| 编辑对象 | 原稿、同一次发生的事实、事实的后续进展分层 | 原稿与事件分组，事件主要是标题近似形成的容器 | 已有事件表不等于已有事件理解 |
| 注意力分配 | 评价事件的重要性、信息增量、证据、读者范围和可用性；选代表稿另做 | 文档信息价值分为主，结合时效和来源数量 | “文章写得具体”与“必须知道这件事”应分开 |
| 阅读时间线 | 分组身份、进展时间锚点和代表稿相互独立 | 代表稿的 ID、日期、收藏状态直接成为卡片状态 | 同一事件可能因换稿而表现成另一张卡 |
| 事实修订 | 原稿修订历史；分析绑定输入版本；旧结果不能覆盖新输入 | 防止短片段覆盖全文，已有链接通常跳过分析 | 防重复花钱的机制同时可能阻止纠错 |
| 个体相关性 | 固定行业与读者群的编辑标准；已读和收藏在浏览器 | 可配置监控、保留匹配关系；综合首页未按个人任务排序 | 这是见微应建立的差异，而不是 AIHOT 已经解决的能力 |

AIHOT 在行业编辑的对象定义与发布一致性上更完整；见微在自定义监控和多 Provider 接入上有适合个人信息台的基础。不能据此宣称 AIHOT 的真实推荐质量更高：本次没有同样本对照，也没有运行其服务。

## 3. 已确认的问题：并非添加功能就能解决

### 3.1 TOP 的候选先被截断，高分内容可能连参赛资格都没有

调用链：`reader-data.ts:676` 每个平台按时间取最多 300 条精选候选 → `content-clustering.ts:175` 按事件代表稿时间排列、来源配额和默认 36 条上限筛选 → `page.tsx:149` 在最终列表内选择 TOP。

**纯函数复现：**37 个独立事件，时间只相差 36 分钟；前 36 个得分 60，第 37 个得分 100。对完整集合排序的第一名是第 37 个；首页流程截断后，100 分事件消失，TOP 第一名变成 60 分事件。这不是陈旧内容应降权的争议，而是排序前裁掉候选的结果。

另外，统一精选每个来源上限 5 条。一个发布方有 6 条独立事件，最后一条得分 100，前 5 条得分 60，即使最终页面只有 5 条也会拒绝第六条。代码叫 `sourceSoftLimit`，但来源限制在补位阶段仍不可突破。

**应该优化：**“近期按时间浏览”和“必须先看”使用各自的选择过程。TOP 应从有明确时间和容量边界的完整候选集合选出，再组织浏览列表；来源多样性作为选集约束，需要为明确重要的任务变化留出例外。数据库层最多 300 条的窗口也需要验证候选覆盖，不能只把 36 改大。

### 3.2 个人监控相关性存在于数据模型，但没有成为综合首页的决策依据

`queries.ts:160` 在指定 monitor 时读取匹配分，没有 monitor 时主要读取文档信息价值分。`page.tsx:38` 只在微信平台加载关键词规则，综合首页并不把 X、搜索等监控统一作为任务优先级入口。

**纯函数加静态 SQL 对照：**一条 MCP 教程的文档价值分 45；配置关键词、教程类型及 MCP/Agent 主题的监控后，`deriveMonitorRetention` 返回保留、相关性分 95。但 `queries.ts:64` 的精选条件始终要求文档价值分 ≥60，即使已指定 monitor 也一样。这条内容可以进保留库或其他视图，却不能成为该任务的精选。

这可以是一个明确的“公共精选”政策，但目前产品又把它当个人信息台主入口。**针对小众任务的关键变化会被大众信息价值门槛压住。**反过来，内容很丰富但不影响用户当前任务的稿件容易通过。

**应该优化：**把来源订阅与任务关注分开。例如关注“某框架升级是否要求迁移”，而不仅订阅某账号或搜索框架名。任务应能表达对象、需要观察的动作和触发条件；对明确符合条件的变化提供优先入口。不要直接把当前匹配分加到文档分上：它是关键词/类型/标签奖励，并不是经过校准的个人效用分。

### 3.3 事件卡片的身份、时间和收藏都依赖代表稿

`groupPersistedEvents`（`content-clustering.ts:153`）按得分和完整度选文章，然后返回 `{ ...primary, relatedSources }`。卡片用文章 ID 建锚点（`timeline-card.tsx:15`），收藏操作也是文章 ID（`:57`）。

**纯函数复现：**11:59 的 70 分文章作为事件代表稿，已收藏；随后进入一篇 11:00 的 90 分文章。事件 ID 没变，但卡片 ID 从 `newer` 变成 `older`，显示日期退回 11:00，卡片显示的收藏变成 false。原收藏没有从数据库删除，它只是属于被替换的那篇文章。

这揭示了一个阅读契约问题：用户在跟踪事件，系统却在不断替换文章。即使增加“已读”字段，如果仍绑定代表文章，换代表稿也会产生假未读。

AIHOT 的 [timeline.ts](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/packages/backend/src/publication/timeline.ts#L2) 明确区分分组 key、时间 anchor 和代表文章；代表稿选择优先一手、全文、分数，再比较时间。新增进展与代表稿更换是不同操作。

**应该优化：**事件有稳定阅读身份；收藏文章与关注事件是两种行为；新增媒体转述不自动制造新进展。只在发生实质变化或需要纠正已展示事实时提示用户。事件页同时保留来源和修改历史，不以换代表稿冒充更新。

### 3.4 标题相似合并无法表达相反事实和事件阶段

**纯函数复现：**“Acme Agent 2.0 宣布向所有用户免费开放 API”和“Acme Agent 2.0 宣布不向所有用户免费开放 API”，不同来源、相差一分钟、主题相同，标题相似度 0.8846，当前规则判断为同一事件。

这两个报道可能是在讨论同一发生，也可能是后续纠正；仅凭两条标题不能认定必须拆卡。但当前存储和展示没有“主张冲突、撤回、更正、阶段变化”的语义，只会选一篇代表并列出其他来源名。相反的主张可能被当成更多来源覆盖（其他标题主要在链接 title 属性里），读者需要自行发现矛盾。

`contentEvents` 与 `eventItems`（`schema.ts:377`）只有标题、规则版本、归属、人工标记及时间，没有事实节点、动作阶段和关系。上一轮的 60 小时窗口修复了时间桥接，**没有解决“什么才是同一件事”**。

AIHOT 的 [group-definitions.md](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/industry/prompts/group-definitions.md) 区分同一次发生、同一事件的新进展、无关和合集；[group.ts](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/packages/backend/src/events/group.ts#L1) 还限制进展直接关联故事起点，避免靠相似邻居无限串联。

**应该优化：**先形成主体、动作、对象、版本/阶段、时间及原文证据的最小事实表示。相似度只负责找候选；候选关系需要判断“重述、进展、纠正/矛盾或无关”。只读标题的强合并应保持保守。无需一开始建设通用知识图谱。

### 3.5 原稿补全与原稿更正没有分开，已有摘要可能继续描述旧事实

**代码路径推断，未运行数据库集成复现：**

1. `ingest-items.ts:286` 发现已有 upstream 身份或 canonical URL 就不进入新分析路线。
2. `repositories.ts:261` 保留已有非空标题；`:262` 只有更长正文才覆盖，等长/更短的官方更正不替换 canonical 正文。
3. 更长新正文可能被写入，但已有成功摘要通常保留，分析状态优先级更新不等于因事实版本变化而重算。
4. `summary-backfill.ts:48` 针对失败、缺摘要、不完整字段补跑，没有“输入事实变化使分析过期”这个范围。

因此，如果正常入库路径收到同链接修订，可能出现旧事实继续显示，或正文和摘要不一致。这里没有声称采集器一定会重新发现每次网页编辑；问题是收到修订后也没有可靠的事实版本处理。

AIHOT 的 [materials.ts](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/packages/backend/src/content/materials.ts#L123) 将跨源发现与原来源修订分开，保存修订版本；[analyze.ts](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/packages/backend/src/editorial/analyze.ts#L455) 检查分析输入版本，旧分析留档但不能覆盖新输入。

**应该优化：**继续防止劣质采集片段覆盖全文，但给原来源的真实修订单独通道。分析缓存和调用去重应绑定输入修订/哈希与分析版本。原稿修订使衍生摘要、事实和事件判断按依赖失效；格式或广告变化不一定要调用模型，更不一定要推送。全文补全、媒体转述、官方更正不能共用“长的赢”。

### 3.6 来源覆盖正在影响重点排序，但它不是独立证据

`featuredEventRank`（`content-clustering.ts:228`）每个其他来源加 6 分，最多加 24 分；来源区分只有平台和来源字符串，无法表达转载链或同一发布主体。

**纯函数复现：**同样时效和完整度，文档分 70、另有 4 个来源的事件最终 116 分，超过文档分 92、没有其他报道的事件（114 分）。排名公式本身正常运算，但它把传播覆盖奖励为重点优先级；没有能力区分 4 个独立验证与 4 个转述同一公告。

AIHOT 的 [hot.ts](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/packages/backend/src/events/hot.ts#L103) 按配置的 group/owner/source 合并参与者，并在增长比较中排除新接入或观察不完整的来源。这更接近衡量观察到的传播变化，**仍不能证明报道为真，也不能自动识别所有转载关系**。

**应该优化：**分别表达影响/个人必要性、传播覆盖、证据强度。热度可以帮助发现值得核对的变化，不能代替事实支持，也不应无条件盖过小众任务的重要更新。

## 4. 最应该借鉴的是编辑标准的拆分

见微现有 prompt 已经要求说明“具体新增了什么”，也禁止空泛理由，不能说它完全没有编辑标准。但模型输入缺少同一事件之前已知的事实和用户读过的版本，所以这句要求主要是在评价当前稿件，无法计算对该事件或该用户的实际新增量。

AIHOT 的 [selection-score.md](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/industry/prompts/selection-score.md) 有三点值得迁移：

1. **事件价值与代表稿质量分开。**短的正式公告也可能很重要；长文、术语和数字多不自动意味着高价值。
2. **宣布动作与证明效果分开。**官方公告可证明宣布上线，不自动证明宣传效果；预告、测试、上线、完成必须保持原文阶段。
3. **重大变化与立即可用分开。**新闻可以重要但不可直接使用；教程可以不重大但对某项任务很有用，评分应体现内容类型和阅读任务。

不建议原封不动复制它的五轴权重。AIHOT 是固定行业编辑，见微有不同的个人任务。该 prompt 的五轴只要求模型在内部计算，输出只有整数；源码不能验证模型实际遵守了内部加权。看起来精确的总分不等于经过校准的效用。

见微更适合在现有主要分析调用中先增加可核查字段：`核心主张 / 动作阶段 / 原文证据位置 / 证据类型`。对事件已有事实做有限比较，再生成“新增了什么、影响哪个关注任务、是否需要行动”。必要性判定和个人影响不能靠一段推荐文案自我证明。

事实保真需要确定性检查与降级：至少校验实体、关键数字、日期、否定词和阶段是否有输入支持；无法支持时保留原文表述或标为待核对。AIHOT 的 [writing.ts](https://github.com/KKKKhazix/AIHOT/blob/3343fe2b20db4be7269113752d82d3992fc52b6b/packages/backend/src/editorial/writing.ts#L214) 有基于已知实体词表的输出检查，可作为局部参考；它也不是完整的事实校验器。

## 5. 见微的主线应变成“关注变化”，而不仅是“阅读更多摘要”

建议以“某 Agent 框架升级是否影响我现有的集成”为一个完整纵向场景，贯通以下行为：

| 新材料到达 | 应怎样更新事件 | 应怎样打扰用户 |
| --- | --- | --- |
| 官方预告新功能 | 记录预告阶段，保留原始证据 | 是否提示取决于关注任务，不能写成已经可用 |
| 多家媒体重复转述预告 | 增加来源覆盖，不新增实质事实 | 已读用户不再因转载收到新变化 |
| 两天后正式开放 | 增加“可用性改变”进展 | 提示“上次是预告，现在可用了”，给出入口 |
| 更换更完整的代表文章 | 改代表稿，不改事件身份 | 已读、关注状态不变，不伪装成进展 |
| 官方更正兼容范围/价格 | 保存修订、重算受影响判断 | 明确提示纠正了之前哪条事实 |
| 新论文只是提到同一框架 | 独立内容或弱关联 | 不强行并入本次升级事件 |

默认入口可以展示“自上次阅读以来与你的关注任务有关的变化”，保留现有最新、归档和主题浏览。已读状态应记录到事件的事实/进展版本；新增来源不一定增加这个版本。首次使用没有阅读基线时，以近期候选及明确关注条件初始化，不能凭空声称了解用户兴趣。

这才是见微对 AIHOT 的发展：AIHOT 已读记录主要是浏览器里的文章 ID（`apps/web/app/lib/local-state.ts:214`），并没有替见微完成事件版本的个人阅读基线或任务影响判断。

## 6. 实现顺序与验收：围绕一个阅读闭环交付

| 顺序 | 具体范围 | 验收标准 |
| --- | --- | --- |
| 第一批：修正当前选择机制 | TOP 独立选候选；来源配额在重要性之后；任务精选与公共精选政策分开 | 37 条反例的高价值事件可被选中；关键任务不被公共门槛静默排除；多样性规则可解释 |
| 第二批：建立事实版本和稳定阅读身份 | 原稿修订 → 分析输入版本 → 最小事实节点 → 事件进展；卡片 key 与代表稿分离 | 短更正能更新事实；旧分析不覆盖新修订；换代表稿不改关注/已读与时间锚点；不会把格式变化当实质进展 |
| 第三批：交付一个任务变化视图 | 明确关注条件、事件阅读基线、“新增/纠正/重复报道”呈现 | 上表完整场景可走通；同事实重复转载不反复提示；新开放/纠正准确出现并带证据 |
| 之后：调校来源和编辑成本 | 记录独有重要变化、提前发现时间、重复贡献及用户标注；对疑难关系选择性使用更强模型 | 不把源的发文数量当贡献；不因低频就关闭关键公告源；模型费用按每条有效变化核算 |

这里的重点是依赖关系，不是先搭一个巨大的事件平台。已有 Provider、回执和监控匹配表可复用，先支持一个清楚的关注对象和动作，再扩展行业范围。队列可以为修订与关系任务提供执行保障，但建完队列并不能宣布阅读闭环完成。

验收也需要变：除了两篇文章是否合并，必须检查**重复材料加入后排序/已读是否稳定、代表稿切换是否稳定、否定与阶段是否保真、关键任务召回、修订能否纠正旧判断**。真实数据上再衡量“必须看到的变化在前 K 条是否出现”“已读后的重复打扰”“读懂一条变化所需时间”。本次没有测得这些指标，不设置虚构的提升百分比。

## 7. AIHOT 不应照搬的部分

- **双评分不是两个独立事实来源。**`analyze.ts:242` 选择一个评分模型并调用两次，有助于采样稳定性；没有证据证明它消除了偏差。先用见微真实样本确认收益，再承担调用成本。
- **官方优先是编辑取舍。**评分输入不提供来源，但 `industry/selection.ts` 的入选阈值按来源层级区分（60/65/76），代表稿也优先一手。适合公告核对，却可能让厂商叙事更容易入选，不能拿来替代独立评测。
- **热度是观察到的传播。**有 owner/group 归并和覆盖校正仍依赖配置完整度，不是全网热度，更不是可信度。
- **行业品味不等于个人必要性。**对普通 AI 重度用户合理的“窄协议/底层优化压低分”规则，对正在维护某协议集成的个人可能正好相反。
- **修订机制也有取舍。**`materials.ts:186` 将任何历史哈希重新出现视为已见版本；能抑制网页轮换噪声，但真实撤回/恢复旧版本也可能不触发新修订。见微需要把“曾见过内容”与“这次恢复动作”区分，不能照抄全部策略。
- **工程分层不能证明质量。**语义召回、关系模型和第二供应商确认都需要在同一批真实样本上验证；更多阶段也会增加故障点、延迟和成本。

## 8. 最终优先级调整

上一轮建议以基础能力列表为主，本轮把产品主线调整为：**先保证重要变化有资格出现，再让事件身份和事实修订可靠，最后围绕用户上次阅读形成增量信息。**

原生 RSS、日报、更丰富的出口和热度图可以保留在后续，但不应抢占主线。若原稿、进展和阅读基线没有分清，日报只会把当前误合并、旧摘要和漏重点变成另一种版式。

对于“借鉴 AIHOT”，应迁移的是编辑对象、时间契约、修订依赖和事实表达约束。对于“优化见微”，应形成的是个人任务驱动的变化阅读闭环。两者结合后才有产品上的进步，而不只是功能表更长。
