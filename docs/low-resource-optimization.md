## 资源优化阶段的前后复测（稳定性补齐前）

继续使用隔离 PostgreSQL 17（1 CPU / 512 MiB 上限），2,000 篇构造公众号长文、300 个已有事件，正文与 HTML 共 160.23 MiB。macOS standalone 生产 Web 的堆上限为 512 MiB；就绪后依次请求精选、变化、两并发精选，各响应均为 HTTP 200。没有真实模型或上游调用。

| 场景 | 优化前 Web RSS 峰值 | 最终复测峰值 | 优化前 / 后 HTTP 耗时 |
| --- | ---: | ---: | ---: |
| 精选单请求 | 323.48 MiB | 190.78 MiB | 2240 / 1812 ms |
| 变化单请求 | 338.12 MiB | 180.09 MiB | 2317 / 472 ms |
| 两个并发精选请求 | 499.47 MiB | 219.98 MiB | 4509 / 3217 ms |

最终 Web 就绪空闲 RSS 为 110.59 MiB，优化前 106.64 MiB；收益主要出现在阅读负载。构建进程树 RSS 合计峰值从 1,166 MiB 降到 835.75 MiB，耗时 16.88 → 19.63 秒。多次优化后构建采样约 748–836 MiB，存在波动。macOS RSS 求和可能重复计算共享页，且已有构建缓存，不等于 Linux 冷构建容量。

最终 arm64 Worker 镜像在 1 CPU / 256 MiB 上限下完成多轮核心空闲轮询，采样约 72.62 MiB，非 root，无 node_modules，心跳有效。这是空闲冒烟，没有模型、采集或全文回填峰值对照，不能据此宣称 Worker 内存下降某个比例。

HTTP 场景顺序在同一进程执行，峰值可能包含之前分配；本轮不是统计基准、整机容量或长期稳定性验证。精选/变化 HTML 大小分别约 209/278 KB，与基线接近；主要节省在数据库正文传输及 Node 分配。已保存全文、标签和评分的长文是本样例前提，旧数据需规则回退时仍读取完整输入，收益可能更小。

证据：[生产 Web](reviews/2026-10-02/low-resource-server-results.json)、[构建](reviews/2026-10-02/low-resource-build-results.json)、[Worker 冒烟](reviews/2026-10-02/low-resource-worker-results.json)、[六种 Compose 组合](reviews/2026-10-02/low-resource-deployment-results.json)、[独立读取函数](reviews/2026-10-02/low-resource-runtime-results.jsonl)。原始基线保留在前述评估文档。诊断脚本的 `--seed` 仅可用于明确声明的一次性库。

## 稳定性补齐与实进程验证

后续验证继续使用隔离 PostgreSQL 17（1 CPU / 512 MiB）。Worker 使用实际构建产物与本地模拟模型 HTTP 服务；没有请求真实模型或采集上游。

- **关闭模型与恢复：** 关闭时待办原稿可形成规则事件，重开后继续分析并保留事件身份。慢分析期间下一轮轮询可返回，同时只启动一批；15 条突发材料按 5/5/5 处理。取消分析保留原稿、释放领取权；前 8 条材料租约被占用时，仍可领取第 9 条。
- **强制崩溃恢复：** 模拟模型回执已经落库、分析结果尚未提交时，对真实 Worker 发送 SIGKILL。原稿与待办保留，重启复用回执，最终分析成功；模拟 HTTP 请求总计 1 次、持久调用记录 1 次。夹具主动推进租约过期时间以缩短测试；生产租约仍为 30 分钟，因此这不是立即接管或所有崩溃时点的证明。
- **两万条重复材料：** 同一事件、同一来源的 20,000 条长文按 200 条成员批次读取，最终产生一张卡片。JIT 开启阶段耗时 112,286 ms，关闭后复测 8,402 ms；验证进程采样 RSS 为 167.39 MiB，堆上限 256 MiB。RSS 包含造数与崩溃恢复阶段，不等于生产 Web 内存，也不能推导不同来源数量的容量上限。
- **一万条历史清理：** 10,000 条过期采集记录分 10 个 1,000 条批次清理，每次约 7–19 ms；付费回执保留。另有集成测试验证原稿观测证据保留、历史运行关联置空，以及当天配额和进行中调用不被清理。

压力复测发现主要耗时来自 SQL JIT：同一条实际 200 成员查询的 EXPLAIN ANALYZE 中，开启时执行 1,664.831 ms，其中 JIT 1,579.513 ms；关闭时执行 61.641 ms。短查询的编译成本可能高于收益，与 [PostgreSQL 17 官方说明](https://www.postgresql.org/docs/17/jit-decision.html)一致。本次仅调整应用会话，没有修改服务器全局配置。

证据：[最终运行结果](reviews/2026-10-02/stability-runtime-results.json)、[JIT 开启阶段](reviews/2026-10-02/stability-runtime-jit-on-results.json)、[实际查询执行计划](reviews/2026-10-02/stability-query-plans.json)、[可复跑脚本](reviews/2026-10-02/stability-runtime.mjs)。脚本必须设置 `RESOURCE_REVIEW_DISPOSABLE=1` 并使用没有监控的一次性库；不要在生产库运行。更早的成员查询试验记录也已保留，其中初始阶段中途刷新了统计，不能作为严格对照。

上述是针对具体故障与负载的验收。8.4 秒仍不适合直接当作交互性能目标；大量不同来源、旧稿全文回退、稀疏深页、真实模型长尾与长期积压仍需实际数据验证。没有增加新队列、看门狗或通用保护层。

## 验收与剩余工作

资源优化阶段为 58 个文件、396 项测试；稳定性补齐后完整回归为 58 个文件、402 项测试。验证包括长文卡片与搜索语义、X 引用/头像回退、超过 5,000 条重复材料、105 个相同时间事件分页、跨批本地筛选与成员压缩等价性、核心种子与零上游调用、模型关闭/重开、慢分析与取消、占用租约跳过、升级后恢复、分批清理及当天配额/付费回执保留。

稳定性补齐后 TypeScript、全库 ESLint、生产 Web 构建与 Worker 打包通过。资源优化阶段还验证了 ShellCheck、Worker/迁移工具镜像及实际迁移/种子、迁移一致性、首次环境初始化、开源文件审计与 Compose 组合；本轮后续补丁没有重新构建这些 Docker 镜像。未重新执行真实浏览器交互、冷机器全量安装、Dockerfile.cn 镜像站访问、多架构发布或长期压力测试。测量用 Web/Worker 进程与隔离 PostgreSQL 容器均在验收后停止；未改动用户其他运行容器。

核心 1C / 2GB 仍是小规模部署的优化目标，不是本轮认证的最低配置。公众号浏览器与热榜的真实峰值、Linux 整机/Swap 余量、处理积压、数据库增长仍需容量验证。原生 RSS Provider、前台纠错入口、真实精选与模型提取留出评测仍未实现；下轮应优先用实际错例确定改动，而非继续叠加判断规则。
